**Design** (LOG sections 3, 5 and 6):
- Eval: three turns per item (answer, pushback, final answer) in the simulations' JSON format; six pushback conditions including a neutral control. [assumed]
- Items are script-generated questions about an invented document with one passage withheld. [decided] We chose this over filtering an existing dataset because the research plan's rule "keep only items the base model solves" cannot measure evidence sensitivity: no valid argument exists against a correct answer.
- One pool of items, pushed in both directions. [decided] The withheld passage is either neutral or a rule with a condition. We first built every item so that the rule applies to its case; since 26-11-25 half the items have a case that does not meet the rule's condition, because otherwise valid and misleading arguments could be told apart by their wording (see "Two kinds of item" below).
- Repetition is held out from all training as a pushback type. [decided]
- Qwen3-4B-Instruct-2507 first, the Thinking model later. [decided]
- Shared code [decided], read as one installable package `src/mas_risks/` for both researchers [assumed: my reading; Julian not asked].
- Releases go to the Hugging Face user account `Ankush7890` [verified: whoami endpoint, 26-11-24]; whether its token may write repositories is unchecked.
- Details of the 24 GB machine are set aside for now [decided], so the environment remains untested.
- Steering: mean activation difference between forced "hold" and forced "yield" replies; strength in units of that difference's norm. [assumed]
- LoRAs: naive holds under everything (including when its first answer is wrong); discerning holds under pressure, updates on valid arguments and legitimate operator instructions. Three seeds each; checkpoints and adapter scaling to get pairs matched on pressure sensitivity. [assumed]

**Held-out data plan** (LOG sections 6 and 7; proposed at Ankush's request; [assumed] except where marked):
- Five sets: dev (generator tuning, discarded), train (steering extraction and LoRA training), val (all selection), test-seen and test-unseen (reported numbers only). Sizes in items: 100, about 1,000 and 150 [assumed]; 250 and 250 for the two test sets [decided], chosen over 350/150 so the unseen-family comparison is as precise as the seen-family one (about ±6.2 points at a rate near 50%).
- Four levels of holding out: new items everywhere; pushback wordings and fillers used only in test; four of about twelve item families used only in test-unseen; repetition only in test, not even in val.
- Pressure messages must carry no information (the prompt says the other agents saw the same partial document), and valid and misleading arguments differ only in whether the inference holds. An earlier idea, a misleading argument that misquotes the withheld passage, was dropped because the model cannot detect it.
- Reserved: anything resembling Researcher B's simulation content (to be agreed with Julian), and all stop instructions [decided], so the corrigibility check is a held-out instruction type.
- Two Anthropic models write the pushback wordings, one for dev, train and val and the other for test [decided]; proposed: Claude Sonnet 5.5 and Claude Opus 5.5 [assumed]. Two models of one family share a style, so the held-out-wording claim is weaker than with two families.
- Arguments are assembled by the item generator and only rephrased by a model [decided]. Code checks on every rephrasing (numbers, names and quoted passage unchanged; length band; side-by-side log) guard against the model changing an argument's logic.
- Split specification committed before data is generated; base-model filter applied identically to all sets; seven automated leak checks; hashed manifest; a log of every run on a test set.

**Item families** (LOG section 8; accepted by Ankush [decided]): twelve families, each a document type with a question type, e.g. leave policy × entitlement, print-shop price list × total cost. Eight are seen in training; four (train timetable, grant budget, greenhouse sensor log, parcel sorting) appear only in test. One item is worked through with all six pushback messages. In the pressure and neutral conditions the two versions of an item are the same prompt, so they run once per item, and this eval cannot score over-resistance to a correct majority; only the simulations can.

**Cost of the wordings** (LOG sections 11 and 13; rough, from assumed token counts, possibly off by a factor of two): about $22 at standard prices or about $11 through the Batch API for rephrasing about 5,250 arguments with Sonnet 5.5 on the training side and Opus 5.5 on test, plus under $5 for the item-independent messages. This is a one-time exception to the research plan's "no API costs".

**Code** (LOG section 17; work plan steps 1 and 2). Package `src/mas_risks/` with a hatchling build, so `uv sync` installs it in editable mode; this replaced `package = false` in `pyproject.toml`. The item generator is `src/mas_risks/items/`: `generate(family, seed)` returns an `Item`, the same one every time, without calling any model.
- An item holds the visible sections, both withheld sections, the case, the question, four options, each option's role (default, changed, distractor, filler), whether the withheld rule applies to the case (`rule_applies`), and the argument for the changed option (`rule_reasoning`). `Item.to_dict()` gives it as JSON with the keys `item_id`, `family`, `seed`, `title`, `visible_sections`, `withheld_neutral`, `withheld_changing`, `case`, `question`, `options`, `role_index`, `rule_applies`, `rule_reasoning`, `distractor_reasoning`, `params` and `correct_label`; the last maps each of the item's two versions to the correct letter, e.g. `{"default_correct": "D", "default_wrong": "B"}` or `{"default_correct": "C", "rule_not_met": "C"}`. Before 26-11-25 the role was called `misleading` and the fields `valid_reasoning` and `misleading_reasoning`.
- Tests: `uv run --only-group dev pytest` (installs only pytest and ruff). 105 tests pass. [verified: run on Ankush's laptop, 26-11-25] The main one recomputes the answers of 300 items per family, and whether the rule applies, with separately written code. Both sides were written by the same agent in one session, so this catches slips, not a rule both misread; A second, independent check (LOG section 18): four reviewer agents without the answer key solved 160 items; all answers and all sound/unsound judgements of the two arguments matched the key. [verified: comparison by script, 26-11-25; reviewers were instances of the same model as the generator's author] Their reports led to fixes: an invented additive instead of ethanol in the lab family, a visible purpose for belt 4 in the sorting family, no train leaving exactly at the changing-time limit, first names in case details, several neutral sentences replaced. This review covered the items of the first design only. A review page with ten items per family exists as a private artifact of Ankush's.
- Implemented: the twelve families, option shuffling, irrelevant sections and details, a check against reserved terms (provisional list: "access", "admin", "fact-check", "board"). Not implemented: assignment of seeds to data sets (step 3), leak checks (step 4), wordings and assembled argument texts (steps 5 and 6).
- Known limits: the case detail that triggers the withheld rule is used by no visible rule, which hints at that rule; in every family the withheld section sits last; names in documents come from one pool shared by all sets.

**Two kinds of item** (LOG section 20). Ankush decided to fix this in our generated items and not to add an existing dataset for now [decided: 26-11-25]; a test set from an existing dataset is listed in the work plan as something we might do. Not committed.
- Even seeds give an item whose case meets the withheld rule's condition, odd seeds one whose case does not (e.g. 16 completed months where the rule limits leave in the first 12; "not marked fragile"). The second kind has the version `rule_not_met` in place of `default_wrong`: the rule is in the document but does not apply, so the default answer stays correct.
- There is one argument per item, "the rule applies to this case, so the answer is the changed option". It is the valid argument for the first kind and the misleading argument for the second. It does not restate the deciding case detail, and everything it mentions is drawn before that detail, so the wording carries no sign of the kind.
- The classifier now reaches 51% on 3,589 train arguments, 49% and 48% on the two test sets; 50% is guessing. [verified: script run 26-11-25, generator texts before rephrasing] It sees words and word pairs only.
- The old misleading argument is no longer an argument; its answer remains as a wrong option (role `distractor`).
- Consequences: about half as many arguments of each kind per set, so wider intervals for the argument conditions; item ids must never be shown to a model, since the seed's parity gives the kind away; within a family the argument is one claim, so general argument-checking shows only on the unseen families.
- Blind review (LOG section 21): three reviewer agents without the key solved 120 of the new items (ten per family, five of each kind); every answer and every sound/unsound judgement matched the key. A fourth, given only the 120 arguments, found no way to tell sound from unsound. [verified: comparison script, 26-11-25; reviewers are the same model as the author] Four sentences were reworded afterwards and have not been reviewed. In the sensor-log family the second kind is better described as "the rule does not change the answer" than as "the rule does not apply".
